I - General Info

The House of Smoke is a technique that relies in its core on the tcache
stashing unlink attack but allows the attacker to return a chunk from malloc 
that is in the main arena without prior libc leak , futher , if the attacker
has read/write access to the malloc-ed chunks , it can result in control over
nearly all the writable libc region after the arena , including IO structures
like stdin/stderr/stdout and IO lists, it's prerequisites are the same as the
House of Lore. 

This trick works on all builds I found  tcache versions up to 2.41, meaning 
from 2.26-2.41, and its breaking on >2.41 is mainly an alignment problem 
rather than by some specific mitigation for this path.

IMPORTANT NOTE : this technique is build specific , there is no checks the I 
found in libc any versions up to 2.44 that prevent it from working , however
things like bin alignement and even compiler optimization can prevent it from 
being applicable , there could be other cases of unpredictable build conditions
breaking the technique.

II - History Of targeting the Main Arena

Exercising control over the arena is not a new trick. The House of Gods
has long since established this exact idea for glibc versions before 2.27
and after 2.23, which did so by replacing the main arena altogether
instead of overwriting it, and it required both a heap leak and a libc
leak [1], meanwhile The House of Mind and its modern fastbin adaptations
does something adjacent by tricking malloc into using a non-main arena for a
specific chunk [2], but that gives us a write-large-value-where primitive
and not control over memory inside the main arena.

With the patching of House of Gods and introduction of tcache, a lot of
focus shifted into mitigating the increasing checks against known techniques
, while other efforts discovered novel ways to return arbitrary chunks from
malloc, among other powerful things; meanwhile the idea of controlling the
main arena was mainly thought of as a possibility by
arbitrary return techniques + libc leak, but not libc-leaklessly.

Aside from these known techniques, little research has focused on
controlling the main arena without a prior libc leak + arbitrary return
technique, or at least I found little during my research.

III - Introduction

III.1 - Achieved primitives & pre-requisites

III.1.a - the achieved primitives
- This technique has two versions :
	- V1
	* return the address of a smallbin in the main arena as a chunk

	- V2
	* return an arbitrary location where we can forge a chunk
	* return the address of a smallbin in the main arena as a chunk
	  immediately after.

	- Further Capability
	* assuming the attacker can read malloc-ed chunks , this provides a 
	  libc leak in the first 8 bytes of the allocated libc address.
	* assuming the attacker has the capability of both reading and  writing
	  to malloc-ed chunks and can repeat the technique , control over 
	  the aread after the arena can be achieved , including IO structures
	  and others.



III.1.b - Prerequisites :
	* V1 :
		* a way to modify the ->bk chunk of a freed pointer.
		* a heap leak
		* a place in memory to forge a fake list of chunks
		* the number of allocations it takes to place a bin in the
		  smallbin (4 in the Poc), one allocation to trigger the
		  chain, and two to retrieve the libc chunk.

	* V2 :
		* a way to modify the ->bk chunk of a freed pointer.
		* a heap leak
		* a place in memory to forge a fake list of chunks
		* the additional requirement to be able to forge a chunk
		  in the area that we want to return from malloc
		* the number of allocations it takes to place a bin the
		  smallbin (4 in the Poc), one allocation to trigger the
		  chain, and two to retrieve the arbitrary target and
		   libc chunk.


III.2 - Introduction to Tcache concepts

III.2.a - The Tcache Structure

Going into all the details of handling Tcache is beyond the scope and need
of this article, but you should know that in libc versions 2.30 to 2.41
the Tcache is initialized on the first call to malloc,
the first chunk in the main arena heap is always a chunk of size 0x290, the
size of the Tcache structure is 0x280 , here is its definition  :

typedef struct tcache_perthread_struct
{
  uint16_t counts[TCACHE_MAX_BINS];
  tcache_entry *entries[TCACHE_MAX_BINS];
} tcache_perthread_struct;
[4]

Note: glibc versions 2.26 to 2.29 use char instead of uint16 for counts,
       which made the structure 0x240 bytes (0x250 as a chunk).

Each entry in counts holds the count of chunks in the bin of the same index
in entries, and each entry in entries is the head of a singly linked list
of chunks of the same size; the bins hold increasingly large chunks with
a difference of 0x10 between the chunk size in a bin and the next, note
that this size difference is only true in the default builds and can be
tuned.

TCACHE_MAX_BINS is by default 64; this means we have 2*64 bytes of
counts and 64*8 bytes of pointers to the heads of bins, totalling 0x280.

When getting a chunk from tcache, tcache_get is called with a specific
bin index, it makes the second-to-head the head, decreases bin count,
and returns the head, meaning it's simply LIFO; tcache_put does the
inverse; it inserts the newly freed chunk as head, and increases the
count of the tcache bin.

The point I want to emphasize here is that we can calculate the location of
the head of any bin in the tcache by knowing where the tcache is, which
we calculate the location of tcache if we have a heap leak and we know the
heap layout.


III.2.b - SmallBin-to-Tcache stashing mechanism

I will be explaining the SmallBin-to-Tcache stashing mechanism in libc 2.41,
which is the latest version this attack works on, and I will be using
source code from that version, but other versions do not differ in
behaviour, and the same PoC works across 2.26-2.41 with no modifications


When __libc_malloc gets a request, it first
checks the Tcache; if it is empty, it calls __int_malloc. If that request
is small-sized , the following code is executed :

if (in_smallbin_range (nb))
{
   idx = smallbin_index (nb);
   bin = bin_at (av, idx);

  if ((victim = last (bin)) != bin)
  {
   bck = victim->bk;
   if (__glibc_unlikely (bck->fd != victim))
     malloc_printerr ("malloc(): smallbin double linked list corrupted");
   set_inuse_bit_at_offset (victim, nb);
   bin->bk = bck;
   bck->fd = bin;

  if (av != &main_arena)
    set_non_main_arena (victim);
   check_malloced_chunk (av, victim, nb);
#if USE_TCACHE
    /* While we're here, if we see other chunks of the same size,
    stash them in the tcache.  */
    size_t tc_idx = csize2tidx (nb);
    if (tcache != NULL && tc_idx < mp_.tcache_bins)
      {
	mchunkptr tc_victim;

	/* While bin not empty and tcache not full, copy chunks over.  */
	while (tcache->counts[tc_idx] < mp_.tcache_count
	&& (tc_victim = last (bin)) != bin)
	{
	if (tc_victim != NULL)
	{
	bck = tc_victim->bk;
	set_inuse_bit_at_offset (tc_victim, nb);
	if (av != &main_arena)
	set_non_main_arena (tc_victim);
	bin->bk = bck;
	bck->fd = bin;
	tcache_put (tc_victim, tc_idx);
         }
     }
 }
#endif
        void *p = chunk2mem (victim);
        alloc_perturb (p, bytes);
        return p;
      }
   }
[5]

The bin is traversed backwards with the ->bk bin pointer , if there is a
chunk in the bin (bin->bk != bin) , the chunk is unlinked , we start with:
           --------------------------------------------------|
           |						     |
         -----        -------       -------                  |
        | bin | -bk->|chunk A|-bk->|chunk B|-bk->....-bk->---|
   --fd-|     |<-fd- |       |<-fd-|       |<-fd-....<-----|
   |     -----        -------       -------                |
   |-------------------------------------------------------|

the lines:
	            bin->bk = bck;
	            bck->fd = bin;
execute with bck being B ,and we end up with : 

           ------------------------------------|
           |				       |
         -----        -------                  |
        | bin | -bk->|chunk B|-bk->....-bk->---|
  -<-fd-|     |<-fd- |       |<-fd-....<-----|
  |      -----        -------		     |
  |------------------------------------------|

However , before the unlinking happens , malloc makes sure the linked 
list is not currupt by verifying that B->fd == A


After the unlinking of A, the tcache of the corresponding size to the
request is located, since the fact that we reached this means that tcache
is empty, malloc proceeds to do the same process mp_.tcache_count times,
which is by default 7 from glibc 2.26 to glibc 2.41, each time a chunk
is unlinked and tcache_put(tc_victim,tc_idx) puts it in the corresponding
tcache, as long as the small bin still has chunks, and the chunks in the
tcache bin have not exceeded mp_.tcache_count(7).

Notice that the check B->fd == A is not done when unlinking chunks for
insertion into tcache; this is a key point on which this technique relies.


IV - Ingredients and Credits

- The classic House of Lore
It is impossible to mention abusing the small bin mechanism without
thinking about the House of Lore. In fact, I have discovered this trick
while fixing a House of Lore PoC implementation; this led me to
find out about the idea of abusing tcache stashing to return arbitrary
addresses and eventually led me to read about the Tcache-stashing-unlink
technique[3].

- The Tcache Stashing Unlink Attack
This is the core mechanism on which House of Smoke builds; normally, it
allows the attacker to return an arbitrary address and to write a libc
address to an arbitrary location; there are, however, differences. In my
method I don't fill tcache like the usual method for this attack does [3],
this allows this technique to avoid some complications that arise from
filling the tcache, such as high malloc count and the need to use calloc.

V - The House of Smoke

V.1 - V1
Suppose we have a chunk in the smallbin, let's call it victim, and we can
corrupt its ->bk pointer to point to a fake freelist constructed in memory
in this fashion:

fake_chunk1-bk>fake_chunk2-bk>..-bk>fake_chunkN-bk->target_tcache_entry-0x10

Note : the ->fd pointer of the head of the fake freelist should point to 
       victim to bypass:
   if (__glibc_unlikely (bck->fd != victim))
      malloc_printerr ("malloc(): smallbin double linked list corrupted");


Note: N is mp_.tcache_count, since we will have to fill the entire tcache,
it is 7 by default in versions 2.26 to 2.41.

Note: we can calculate the address of tcache because we have a heap leak,
as long as we know the heap layout, which we do if we can make and predict
mallocs made by the program, we can calculate the exact size
entry inside the Tcache.

Now, if we call malloc on that exact smallbin size, first the victim chunk we
corrupted the ->bk of gets unlinked and stored in victim (in the process
the ->fd of our fake freelist's head is checked to be equal to victim ),
and the tcache loop starts filling the corresponding tcache bin with a 
chunk from our fake freelist, but when we reach the final iteration, where 
the last element of the freelist is unlinked :
	            bck = tc_victim->bk;
...
	            bck->fd = bin;
	            tcache_put (tc_victim, tc_idx);

The Address of the smallbin is written to (fake_chunkN->bk)->fd; remember
that fake_chunkN->bk points to an entry in the Tcache that already has a chunk
this means that the bin address gets written as the Tcache bin's head,the last 
element of the fake list is inserted normally after that , while the 
overwritten tcache entry now holds a bin address.

What follows is one malloc of the size of the tcache entry that we write the 
bin address in ,yields the SmallBin address.
Note : the target tcache entry should already have a chunk in it so the chunk
count for that entry is > 0 , this can be done by allocating a chunk of that
size and freeing it , we then overwrite its address in the entry win the bin.

Note: we don't need to worry about safe-linking because we write the head
to tcache, which stores the bin heads without mangling them, and libc
handles the mangling/unmangling itself when we insert/retrieve chunks
after.

V.2 - V1-PoC

This has been linked and tested against glibc 2.41 , the assertion passes

#include <stdlib.h>
#include <assert.h>

int main(int argc, char * argv[]){
	//the smallbin chunk we will overwrite the bk of
	char *victim = malloc(0x510);
	char *tcache = (char*)victim - 0x290;
	//to avoid consolidation with top
	char *guard = malloc(0x1000);
	//put victim in unsorted bin
	free(victim);
	//allocate a chunk that will be cut from victim
	//the size of the remainder is 0x110(with metadata)
	char *trim_victim = malloc(0x400);

	//update victim to reflect the trim
	victim =  trim_victim + 0x410;
	//the victim including metadata
	char **victim_chunk = (char **)victim-2;

	//the chunk we will overwrite in its tcache entry
	//its entry is the one immediately following the one
	//corresponding to victim size
	char *tcache_target = malloc(0x110);
	tcache += 0x80 + (int)(0x110/0x10 - 1 )*8 ;
	//sort victim into the small bin
	//this progression bypasses filling the tcache
	//so 6 less allocations
	void *p2 = malloc(0x1000);
	//putting tcache_target in tcache
	free(tcache_target);

	//keep the address of the smallbin for later sanity check
	char *smallbin = victim_chunk[2];

	//create a fake freelist on the heap , we can use
	//the trim result for that
	char * (*freelist)[4] = (char * (*)[4])trim_victim;
	//links the fake list chunks
	for(int i=0; i<6; i++) {
		freelist[i][3] = (char*) freelist[i+1];
	}
	//to bypass the smallbin fd check
	freelist[0][2] = (char *) victim_chunk;


	//the address of the smallbin will be written to
	//(freelist[6]->bk)->fd
	freelist[6][3] = (void*)tcache-0x10;

	//------------VULNERABILITY-----------
	victim_chunk[3] = (char *)freelist[0];
	//------------------------------------

	//this allocates victim and starts filling tcache with chunks from
	//our freelist
	char *p3 = malloc(0x100);
	//this allocates the smallbin address
	char **p5 = malloc(0x110);
	assert((long)p5 == (long)smallbin);
	exit(0);
}

V.3 - V2

It is the same in principle, and suppose this time we have a target in
memory where we want to get a chunk and we can write a pointer there,
we can create a fake freelist of size N-1, link the target chunk as
->bk of the freelist tail, and link the tcache entry address(-0x10)in
the bk field of target, so the whole list is :

fake_chunk1-bk>..-bk>fake_chunkN-bk->target-bk>tcache_size_entry-0x10

Following the same mechanism as V1, the first allocation after triggering
the chain will be target, and the second will be the Smallbin address.

	//corresponding to victim size

VI - Why It Does not Work On glibc >= 2.42?

VI.1 - The Hidden Dependency

Starting from glibc 2.32 [6][7], tcache_get checks if chunks are aligned
to 0x10 on 64bit architectures and 0x8 on 32bit architectures before 
returning them :

...
tcache_get (size_t tc_idx)
{
  tcache_entry *e = tcache->entries[tc_idx];
  if (__glibc_unlikely (!aligned_OK (e)))
    malloc_printerr ("malloc(): unaligned tcache chunk detected");
...[7]

I am considering the 64-bit architecture here; this is a problem because
while the bin addresses in the main arena are typically aligned to 8,
they are not necessarily aligned to 0x10 , they aligned to 0x10 on all the
builds I have found and tested and/or built myself, from versions 2.26 to 
2.41 , the builds (arch & ubuntu) versions 2.42 and higher, however, all 
seem to have the bin addresses only aligned to 8, this making tcache panic 
when returning the bin address.

VII - Seeing Beyon The Smoke, What can you Do?

VII.1 - Assuming read capability
This one is simple; the address returned points directly to a libc address
since every bin's links are populated by the bin's own address, so any kind
of read, whether by write or printf or similar, should leak a libc address.

adding a  printf("%p\n",alloc2[0]); to the previous PoC prints a libc 
address.

VII.2 - Assuming read/write

Here is where it starts to become Interesting; the bins are a truth 
reference in malloc, and not only are they trusted, but they are also used
a lot for checks to validate linked list integrity, etc. The ability to 
write to a bin gives us the ability to implant a chunk in a bin, as long 
as we can also fake the links in the chunk; this leads to an interesting 
scenario where we can "expand" our control in the libc memory region.

Suppose we have our read and we leaked libc after the initial House of
Smoke, now we can simply :
* write the address of a bin that is further ahead to the links of the
  immediate bin we returned the address of
* write a proper prev_size and size to the bin we wrote the address of
  our immediate bin, and after that write the address of our immediate
  bin as the chunk links.
* allocating a size that corresponds to our immediate bit will return
  the further bin's address.

As a proof of concept, add these lines to one of the PoCs above:

	//now we assume the attacker can read from alloc2 an address of libc
	//this is why this require both read and write capability
	//
	//get the address of the eith bin forward
	char **bin2 = alloc2;
	char **bin1 = alloc2;
	char *alloc3 = NULL;
	//make sure we started before stdout
	assert((long)alloc2 < (long) stdout);
	char *backup[4];
	while ((void *)alloc3 < (void *)stdin + 0x300){
		bin2 += 28;
		//simulate a write
		//fake links of current bin to point to the next allocated one
		bin1[0] = bin1[1] = (char *) bin2;
		//backup bin2 contents to restore them and avoid crashes
		//we are overwriting ciritical libc data with our fake
		//chunk , this goes with the assumption that the attacker can
		//read/write to malloced chunks , and bin2 chunk is entirely
		//within either bin1 or alloc3 , so no hidden dependencies
		for (int j = 0 ; j < 4 ; j++){
			backup[j] = bin2[j];
		}
		//fake sizes
		bin2[0] = bin2[1] = (char *) 0x100;
		//fake links of the next bin to point to point to current bin
		bin2[2] = bin2[3] = (char *) bin1-0x10;
		alloc3 = malloc(0xf0);
		assert((long)alloc3 == (long)bin2+0x10);
		//restore state
		for (int j = 0 ; j < 4 ; j++){
			bin2[j] = backup[j];
		}
		
	}
	//by now we reached beyond stdin+0x300 , which is not far off the
	//end of libc writable region
	exit(0);


This allows an attacker to "expand" in the writable libc region after the 
main arena.
